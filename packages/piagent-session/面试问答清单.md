# 会话持久化模块 · 面试问答清单

> 用法：不要背答案，理解每题背后的“为什么”。面试官问的是判断力，不是记忆力。
> 每题给了「一句话结论 + 展开」，面试时先给结论，对方感兴趣再展开。

---

## 一、持久化设计

**Q1：Agent 的状态是什么？为什么需要持久化？**
结论：Agent 的唯一状态就是那个 messages 数组（对话历史），它决定了下一步模型看到什么。
展开：模型本身无状态，每次调用都要把完整历史喂进去。历史只存在内存里，进程一挂就全没了——用户几十轮的对话、工具执行结果全部丢失。持久化就是把这个唯一状态落到磁盘，让会话可中断、可恢复、可回溯。

**Q2：为什么用 JSONL 追加写，而不是每次把整个会话 JSON.stringify 后覆盖文件？**
结论：追加写在崩溃安全和写成本上都更优。
展开三点：
1. **崩溃安全**：全量覆盖如果写到一半崩溃，整个文件可能损坏，全部历史丢失。追加写每次只往文件尾加一行，崩溃最多让最后一行不完整，前面全部完好。
2. **写成本**：全量覆盖每加一条消息就重写整个文件，累计是 O(n²) 的 IO 放大。追加写每条只写自身，累计 O(n)。
3. **可审计/可回放**：一行一事件，本身就是一份操作日志（事件溯源思想）。

**Q3：追加写的代价是什么？你怎么权衡？**
结论：代价是读取时要重放整个文件来重建状态。
展开：对话历史通常不长（几十到几百条），全量重放可接受。如果真的很长，标准做法是「周期性快照 + 增量日志」：定期把当前状态存成一个 snapshot，之后只追加增量，恢复时读最近 snapshot + 重放其后的增量。我这版没做，因为它属于后续优化，当前规模用不上——避免过度设计。

**Q4：进程正好在写一行的中途崩溃，文件尾部留了半行非法 JSON，怎么办？**
结论：恢复时逐行解析，最后一行解析失败就当崩溃残留丢弃；中间行失败则抛错。
展开：这是崩溃安全的关键细节。半行只会出现在文件末尾（追加写的特性）。所以策略是：解析失败时判断它是不是「最后一个非空行」——是就安全跳过（崩溃残留），不是就说明文件被外部损坏了，抛错让上层知道，绝不静默吞掉。我为这个场景专门写了测试用例。

## 二、会话树 / time-travel

**Q5：为什么要把线性的 messages 数组升级成一棵树？**
结论：数组无法表达「回到历史某个点，走另一条路」。
展开：很多真实需求是分支式的——同一个问题想让模型换个方式再答一次、A/B 对比两种 prompt、从某步重跑。线性数组要么覆盖历史（丢失原分支），要么整段复制（冗余且难管理）。树用 parentId 把每条消息挂到父节点上，「分叉」就是从某个非叶节点再长一个子节点，原分支完全不受影响。这跟 git 的分支模型是同一个思想。

**Q6：怎么实现 time-travel？**
结论：维护一个 HEAD 指针（类似 git HEAD），checkout 把它移到历史节点，之后 append 就从那里分叉。
展开：取「喂给模型的历史」时，从当前节点沿 parentId 一路上溯到根再反转，就是一条完整的消息链。所以切换分支只是移动 HEAD，不涉及任何数据拷贝，O(1)。

**Q7：为什么把树结构和持久化拆成两个类？**
结论：关注点分离——树只管逻辑，存储只管落盘。
展开：`SessionTree` 是纯内存、无 IO 的，可以脱离磁盘单独单元测试；`JsonlStore` 只管追加和读取。想换存储后端（比如换成 SQLite）只改 store，树一行不用动。`Session` 门面把两者组合起来。这种分层让每一块都可测、可替换。

## 三、集成与工程

**Q8：这个持久化层是怎么接进 Agent Loop 的？改了内核吗？**
结论：零侵入。runAgent 那 100 行一行没改，全靠既有的 onEvent 事件钩子挂进去。
展开：内核在 agent_start / assistant / tool_end 等时机会 emit 事件。我写了个 persistOnEvent 适配器，订阅这些事件、在对应时机把消息 append 落盘。这正好体现了当初把「生命周期事件」设计进内核的价值——扩展能力不靠改核心，靠挂钩子。

**Q9：多个会话并发写、或同一会话多标签页并发，会有问题吗？**
结论：当前用同步追加写保证单会话内不交错；跨进程并发是已知边界，是下一步要解决的问题。
展开：同步 appendFileSync 保证「写完才返回」，单进程内多次 append 不会交错。但如果两个进程同时写同一个文件，仍可能交错——生产级方案是给会话文件加锁（flock）或每个「会话通道 lane」独立文件。诚实说出边界比假装没有更好，也正好引出 pi 里 multi-lane 的设计。

**Q10：你测了哪些场景？**
结论：正常恢复、崩溃半行容忍、分支分叉、append-only 不重写、事件流落盘，共 6 个用例。
展开：重点讲「崩溃半行」那个——我手动往文件尾追加一段非法 JSON 模拟崩溃，断言恢复后仍能拿到之前完好的消息。这类「异常路径」的测试比「正常路径」更能体现工程严谨度。

## 四、拔高 / 对比 PI

**Q11：这和工业级实现（PI Agent）比，差在哪？**
结论：核心思想一致（JSONL 会话、会话树、time-travel），我砍掉了生产环境才需要的复杂度。
展开：pi 还有原子发布（tmp+rename）、写操作串行化队列、seq 完整性校验、SQLite 后端、多 lane 并发隔离、上下文压缩等。我这版聚焦「会话持久化 + 恢复 + 分支」这条主干，把它做扎实、做到可测。我的路线是先实现最小闭环理解本质，再逐层逼近生产级——下一梯队就是上下文压缩。

**Q12：如果让你继续做，下一步是什么？**
结论：短期补原子发布 + 写串行化；中期做上下文压缩（Compaction）。
展开：原子发布和写串行化改动小、价值高，能把崩溃安全和并发提到生产档次。再往后是长对话迟早撑爆 token 窗口的问题：当历史超过 token 预算时，用模型摘要旧消息、保留工具调用结果等关键信息。难点在「摘要什么、保留什么」的策略权衡。
