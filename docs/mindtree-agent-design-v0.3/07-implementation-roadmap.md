# 实施路线与代码落点

## 1. 当前基线判断

MindTree 0.2.2 已具备：

- `MindMapDocument` 和丰富节点语义。
- Command 执行、撤销重做和持久化。
- AI 请求、分支/计划生成与预览确认。
- 任务中心、摘要、导出和 MCP。
- 工作区备份恢复。

因此新功能应复用现有结构，不新建平行编辑体系。

## 3. 里程碑 0：技术债检查

在新增功能前完成：

1. 核对客户端、服务端和 MCP 的文档结构是否同步。
2. 特别检查 MCP `MapPayload` 与当前节点新增的 `marks`、`tagIds`、`width`、`height` 等字段兼容性。
3. 确认跨文档写入和版本机制的真实能力。
4. 为 Dexie schema 升级建立测试样例。

这一步只修复会阻塞沉淀功能的问题，不扩大重构范围。

## 4. 里程碑 1：纯领域模型与解析

交付：

- 候选类型和 Zod schema。
- 模型输出解析。
- ID 白名单验证。
- 指纹和重复检测。
- 候选到应用操作的转换。
- 使用日报、学习、项目、灵感四类固定样本测试。

这一阶段不调用真实模型，不做 UI。

审查点：协议是否足够表达“新增、更新、完成、追加备注”，是否避免过度生成。

## 5. 里程碑 2：本地持久化

交付：

- Dexie `depositBatches`、`depositProvenance` 表。
- 迁移和旧数据库兼容。
- 批次 CRUD。
- 已应用指纹查询。
- 备份/恢复策略：第一版至少明确是否包含候选和来源。

建议：工作区备份包含已应用来源；未处理候选可包含，也可明确暂不包含，但必须文档化。

## 6. 里程碑 3：上下文与 AI 调用

交付：

- 当前节点/子树上下文构建。
- 目标文档和节点候选选择。
- 专用 prompt。
- 调用现有 `requestAiChat`。
- 错误、空结果和上下文过大处理。

审查点：实际发送内容应可在开发模式查看，确认没有无关数据和秘密。

## 7. 里程碑 4：待沉淀收件箱

交付：

- 生成沉淀建议入口。
- 候选列表。
- 类型、动作和目标编辑。
- 忽略、接受和批量选择。
- 可能重复/目标缺失提示。

这一阶段先允许只应用到当前文档；跨文档选择可以显示但暂不开放确认，避免 UI 和事务同时膨胀。

## 8. 里程碑 5：单文档原子应用

交付：

- `APPLY_DEPOSIT_OPERATIONS` 或等价领域命令。
- 差异预览。
- 一次确认、一次撤销。
- 来源写入。
- 节点删除或文档变化后的冲突处理。

审查点：失败不得产生半写入。

## 9. 里程碑 6：跨文档回流

这是产品价值真正闭环的阶段。

交付：

- 目标文档选择。
- 工作区级事务。
- 文档版本检查。
- 跨文档结果导航。
- 工作区级撤销或明确的补偿操作。

如果不能可靠整体撤销，必须在界面明确跨文档写入边界，不得假装使用当前单文档撤销即可恢复。

## 10. 里程碑 7：低打扰提示与验证

交付：

- 随手记/日期分支的本地提示规则。
- 文档级关闭提示。
- 用户真实使用日志：接受率、修改率、忽略率、重复率。
- 根据结果决定是否进入智能协作状态机。

## 11. 后续版本

在 MVP 被真实使用验证后再实现：

- 探索/决策/交付协作会话。
- 阶段检查点。
- 决策记录和知识卡模板。
- MCP 沉淀工具。
- 更强的跨图检索与关联。

## 12. 不建议并行实施的内容

- 向量检索。
- 多 Agent。
- 自动后台循环。
- 全历史批量整理。
- 大规模 UI 重构。
- 复杂知识图谱。
