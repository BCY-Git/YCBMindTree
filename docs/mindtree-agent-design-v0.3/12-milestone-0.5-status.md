# 里程碑 0.5 实施状态

更新时间：2026-07-15

## 目标

让外部 Agent 能通过 MCP 读取受限上下文、生成并预览智能沉淀候选，同时确保任何导图写入仍需要显式确认和版本校验。

## 已完成工具

- `mindtree_analyze_deposit`：只读指定节点的有限子树，不返回附件或无关分支。
- `mindtree_preview_deposit_plan`：校验候选类型、动作、来源 ID 和目标 ID，保存待审查批次但不修改导图。
- `mindtree_list_deposit_batches`：按状态列出当前用户批次摘要，不返回确认令牌。
- `mindtree_apply_deposit_plan`：要求一次性确认令牌、`confirmed=true` 和匹配的文档版本。

## 受控流程

```text
Agent 读取有限子树
→ Agent 根据协议生成候选
→ 服务端校验并生成预览
→ 用户在 MCP Host 核对变化
→ 携带一次性令牌显式确认
→ SQLite 单事务保存导图与批次状态
```

## 安全边界

- 分析工具是只读工具，不会创建批次或修改导图。
- 预览只保存服务端批次，不产生节点写入。
- 候选只能引用分析范围内的来源节点和当前目标导图中的节点。
- 第一版 MCP 计划限制为单目标导图，确保原子写入；跨导图仍使用客户端已验证的 Dexie 事务流程。
- 应用前重新检查版本；预览后导图变化会拒绝整批写入。
- 导图与批次状态在同一 SQLite 事务中更新，不产生半完成状态。
- 批次列表不泄露确认令牌；应用后令牌立即清空。
- MCP 不具备删除、移动、合并或无确认自动写入能力。

## 客户端桥接决策

0.5 不把服务端 MCP 批次同步进客户端本地 Dexie 收件箱。两者属于不同持久化域，强行桥接会制造重复批次、版本竞争和来源状态不一致。

当前采用明确降级：MCP 计划由 MCP Host 完成预览确认；MindTree 客户端通过现有文档同步获得最终导图版本。以后若需要统一收件箱，应先设计批次同步协议和唯一来源身份，不能只复制 JSON。

## 验证

- 受限子树上下文测试。
- 候选来源与目标白名单测试。
- 预览不修改文档版本测试。
- 确认令牌、显式确认与版本匹配测试。
- 批次按用户隔离和令牌不泄露测试。
- 导图与批次状态原子提交测试。
- 服务端全量测试与 TypeScript 构建。
