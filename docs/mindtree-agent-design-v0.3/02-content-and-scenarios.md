# 内容类型、信息层次与真实场景

## 1. 三层信息结构

### 记录层

允许信息不完整、不分类和混合：日报、周报、随手记、会议原话、临时想法、当时判断。

### 工作层

用于持续推进的对象：项目、学习主题、任务、问题、风险、待验证假设。

### 沉淀层

未来仍有价值的信息：最终决策、已验证结论、可复用经验、知识卡、阶段总结、踩坑与修复方式。

记录层不因沉淀而删除；工作层可以持续更新；沉淀层应保持低噪声。

## 2. 第一版内容分类

| 类型 | 定义 | 默认处理 |
| --- | --- | --- |
| `fact` | 已发生的客观记录或沟通 | 保留原处，可追加项目时间线 |
| `result` | 已交付、已完成或形成的成果 | 更新项目进展或完成任务 |
| `task` | 明确需要执行的动作 | 创建或更新任务 |
| `problem` | 未解决问题、阻塞、风险 | 创建问题/风险节点 |
| `decision` | 已选择的方向及理由 | 写入决策分支或备注 |
| `knowledge` | 稳定定义、边界、经验或结论 | 写入知识主题 |
| `idea` | 尚未验证的可能性或灵感 | 进入想法收集或关联项目 |

一个源节点可产生多个候选；一个候选只能有一个主类型，可附加标签。

## 3. 场景 A：日报/周报

输入通常按日期组织，混合事实、结果、任务、问题和沟通。

Agent 应提取：

- 今日完成
- 仍在进行
- 新问题或风险
- 产生的决策
- 对外沟通与交付
- 下一步
- 可能关联的项目

Agent 不应：

- 重写或删除日期树。
- 为每一天创建重复的“当前状态”骨架。
- 把模糊意图强行标记为已确定任务。

## 4. 场景 B：学习记录

输入包含个人理解、AI 定义、重点、示例、纠偏和概念关系。

Agent 应识别：

- 概念名称
- 用户当前理解
- 标准或候选定义
- 关键边界
- 示例与反例
- 曾出现的误区
- 待验证问题
- 理解成熟度

第一版不必新增复杂“掌握度”字段，可用标记和备注表达：`待验证`、`已通过新案例验证`。

## 5. 场景 C：项目记录

输入围绕同一目标持续更新。

Agent 应优先判断：

- 新建节点还是更新已有节点。
- 是否完成了现有任务。
- 是否改变了约束或验收标准。
- 是否形成关键决策。
- 是否需要阶段检查点。

## 6. 场景 D：临时想法

Agent 只需提供低压力建议：

- 保持独立想法。
- 关联已有项目。
- 转为待验证假设。
- 转为任务。
- 暂不处理。

不得因为无法判断去向而阻止保存。

## 7. 内容路由原则

1. 优先建议已有文档和节点，不默认新建重复项目。
2. 置信度不足时建议进入“待整理”，不强行归类。
3. 更新已有内容优先于重复新增。
4. 原始记录与沉淀结果之间必须保留来源关联。
5. 沉淀候选可以跨文档，但第一版可以先限制为本地工作区内目标。

## 8. 典型用户故事

### US-01 日报回流项目

作为用户，我按日期记录工作后，希望系统找出其中与已有项目相关的成果、问题和下一步，以便我确认后更新项目状态。

### US-02 学习结论沉淀

作为用户，我记录个人理解和 AI 解释后，希望系统区分稳定结论、误区和待验证问题，而不是简单生成更多解释。

### US-03 临时想法保留

作为用户，我想快速写下想法，不希望先选择分类；稍后系统可以建议它与某个项目关联。

### US-04 避免重复沉淀

作为用户，我不希望同一条日报在多次分析后重复创建任务或项目节点。

### US-05 可追溯回原文

作为用户，我希望知道某个项目结论来自哪一天的哪条记录，并能回看当时原文。
